# S53 review packet — 0B-1 (C1): reviewed candidate = published candidate

**Work item (brief):** C1 — coherent release candidate and revision boundary.
**Acceptance gate:** Reviewed candidate is exactly what publishes; failed or
concurrent reads cannot silently make partial content.

## Source findings (verified)
- Publish snapshotted the CURRENT mutable drafts with nothing identifying
  what the merchant actually reviewed — edits landing between review and
  publish went live unseen.
- snapshotContent degraded silently: a pages read failure became `pages: []`
  and any getBlockRow failure became "not customized" — a transient error
  could freeze a PARTIAL snapshot into an immutable release.
- Ordinary API clients could skip the revision/conflict check by simply
  omitting `revision`; reset and deletePage had no revision guard at all, so
  a reset racing a colleague's save silently discarded their work.

## Changes
- `createRelease({expectedDraftHash})`: when provided and the fresh snapshot
  hash differs → 409 `DRAFTS_CHANGED`, no release row created. The releases
  API passes it for publish AND schedule; ReleasesAdmin sends the draftHash
  whose diff the merchant is LOOKING at, and on 409 adopts the fresh view
  (the updated change list renders) with a persistent banner. The candidate
  identity is the content hash — no new tables.
- `snapshotContent` is STRICT: getBlockRow gains a strict mode (only
  "no such table" still reads as absent — the genuine pre-migration state);
  a pages read failure throws "release snapshot failed reading pages".
- Revision required at the API: block/page saves without `revision` are 428
  `REVISION_REQUIRED`; the deliberate overwrite is the EXPLICIT `force:true`
  (audited with `forced: true`). reset/deletePage accept an optional
  revision with CAS semantics (deleteBlock/deleteContentPage in
  lib/cms/store.js; already-gone rows stay idempotent). Lib-level functions
  keep optional semantics for scripts/seeds/privileged writers (applyKit,
  experiments adopt, AI insight apply — unchanged, as recorded in the audit).
- Console kit updated: cms/api.js saveBlock/savePage take `{force}`;
  resetBlock/deletePage pass the loaded revision. All five overwrite/reset/
  delete call sites updated (HomeEditor, NavigationEditor, PdpExtrasEditor,
  PageEditor, PagesList — list now wires pageRevisions into delete).

## Compatibility impact
- BREAKING for raw API clients that previously saved without `revision`
  (now 428 with a self-explanatory error + the `force` escape hatch). The
  shipped console always sent revisions; scripts use the lib layer.
- Schedule honesty unchanged (snapshot at schedule time) but now also bound
  to the reviewed hash at the moment of scheduling.
