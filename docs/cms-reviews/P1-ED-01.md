## Fix round 1

An independent review found one blocking problem and nine smaller ones. Each was checked against the code first.

### Blocking: on the designer, a page that fails to load left no navigation and no sign-out. Confirmed, fixed

**The review was right.** On editor routes `ConsoleShell` renders only the nav drawer and `<main className="min-w-0">`; the only button that opens the drawer is in `EditorShell`'s top bar. When the page throws, Next shows the `(authed)` error boundary (`app/(console)/admin/(authed)/error.js`) in place of the page, so `EditorShell` never mounts and nothing can open the drawer. The same was true of the `(authed)` loading skeleton. At `bdbe1a7` the sidebar was outside the page, so it survived; the S50 comment ("a failing admin page keeps the shell") stopped being true on this branch.

**Reproduced first, two ways.**
- **Rendered test**, written before the fix and run against the original `error.js`, `loading.js` and `ConsoleShell.js` (mutation R1 below): 3 failed, for example `✗ on the designer, a page that fails to load still has the menu (navigation and sign-out) and the usual padding` and `✗ on the designer, the console's menu really opens the store navigation drawer`.
- **Browser**, on the harness, with a temporary `throw` in `app/(console)/admin/(authed)/storefront/designer/page.js` (reverted with `git checkout`, not committed), measured by a scratch probe over the DevTools protocol:

| | Visible buttons | `/admin` links reachable | Error message (`role=alert`) at 1440 |
|---|---|---|---|
| Original shell and error page | `Try again` only | 0, no way to open the menu | 1390px wide, its card 25px from the window edges |
| Fix round 1 | `Open menu`, `Try again` | `Open menu` opens the drawer: 23 links and `Sign out` | 926px, its card inside the console's usual padded 1024px page |

Same result at 800 wide. Screenshots: `drills/ED-01/fix1-error-before-1440.png`, `fix1-error-before-800.png`, `fix1-error-after-1440.png` and `fix1-error-after-800.png` (both taken with the menu open, showing the navigation and Sign out).

**The fix.**
- **`ConsolePageFrame`** (new, in `components/console/nav/ConsoleShell.js`). On an editor route it lays out anything that is not the editor: a small top bar with the `Open menu` button and the store's name, then the content in the console's usual padded, capped page (`mx-auto max-w-5xl px-4 py-6 sm:px-6`). Anywhere else it returns its children untouched. It reads the shell's context, which on editor routes now carries `editor: true` and `storeName` beside `openNav`.
- **`app/(console)/admin/(authed)/error.js` and `loading.js`** wrap their content in it. So it follows `EDITOR_ROUTES`: a future editor route gets the menu on its error and loading pages with no new file. On every other console page both render exactly as before (tested).
- **`app/(console)/admin/(authed)/storefront/designer/loading.js` (new).** While a designer page loads, it shows the editor's own shape (top bar with the menu, then tree, preview and inspector skeletons; no tree on the product and collection designers) instead of the console's page skeleton. This also closes the old known limit about a full-width, unpadded loading skeleton.

Rendered tests (in `test:editor-layout`): `✓ on the designer, a page that fails to load still has the menu (navigation and sign-out) and the usual padding` (all three designer routes: `AdminError` inside `ConsoleShell`, asserting an `Open menu` button before the error, the store name, and the padded page), `✓ on the designer, the console's loading skeleton has the menu too`, `✓ the designer's own loading state is editor-shaped, with the menu, and a tree only on the home page`, `✓ on every other console page the error and loading pages are as before: no extra bar`, and `✓ on the designer, the console's menu really opens the store navigation drawer` (calls the shell's `openNav` and checks the drawer opens).

## What was built

- **`components/admin/cms/editorLayout.js` (new, no JSX, no imports).** The editor's numbers in one place: the editor routes, tree 224px, inspector 288px, canvas padding 8px, breakpoints 1280 and 1024, the three devices (Mobile 375, Tablet 768, Desktop 1280), how a device's page fits the space (`frameFit`, `frameStyles`), the caption (`fitCaption`) and the expected pane widths at any window width (`editorGeometry`). The shell, the unit suite and the drill all use these numbers.
- **`components/admin/cms/EditorShell.js` (new).** `EditorShell` is the editor's own layout outside the console's cap: a compact top bar (menu button, the store's name from 1280 wide, Sections button below 1280, breadcrumb, title, surface tabs, the caller's actions), a notices strip, and the panes: tree on the left, preview in the centre, inspector on the right. From 1024 wide it fills the window below anything the console shows above it, so the page itself never scrolls and each pane scrolls on its own. Below 1280 the tree renders in a drawer (the console's own `Drawer`, a native modal `<dialog>`), and in exactly one place at a time; picking a section there closes the drawer. `DeviceSwitch` is the Mobile, Tablet and Desktop buttons, with `aria-pressed` and a tooltip giving the width. `PreviewCanvas` measures its own space, renders the page at the device's real width, shrinks it as a whole when it does not fit, and shows a caption such as `Desktop, 1280 px wide, shown at 71% to fit`.
- **`components/console/nav/ConsoleShell.js`.** On editor routes (`/admin/storefront/designer` and anything under it) the shell renders no sidebar, no 1024px cap and no page padding. The navigation folds into the existing drawer, which the editor opens from its menu button through `useConsoleNav()`. `ConsolePageFrame` (fix round 1) gives the error and loading pages on those routes the same menu. Every other console page renders exactly as before. The founder's saved sidebar preference is untouched.
- **`components/admin/cms/Designer.js`.** Uses `EditorShell`. The tree and inspector lose their card wrappers, because the panes have their own dividers. Each tree row's own button is marked `data-tree-pick`. The preview uses `DeviceSwitch` and `PreviewCanvas`, and the old `DEVICES` list with `width: "100%"` is gone. Save, the save status, the conflict and error banners, preview start and refresh, and the PreviewBridge handshake are unchanged. The banners are now the shell's children; their lines are byte for byte the same.
- **`components/admin/cms/SurfaceDesigner.js`.** The same shell with no tree: preview in the centre, the Template, Modules and "Also on this page" cards in the inspector. Before a product or collection is picked, the centre asks for one and there is no empty inspector. The cards moved into a `const inspector`, so their lines are re-indented; `git diff -w` shows them unchanged.
- **`app/(console)/admin/(authed)/error.js`, `loading.js`, and `storefront/designer/loading.js` (new)**: fix round 1, above.
- **`components/console/Drawer.js`.** A `closeLabel` prop, default `Close menu`, so the tree drawer's close button reads `Close sections`.
- **`components/admin/cms/DesignerTabs.js`.** Its bottom margin is dropped, because it now sits in the top bar.
- **`scripts/test-editor-layout.js` + `test:editor-layout` (new suite, in the gate).** Unit tests of the numbers; rendered tests of the real `ConsoleShell`, `Designer`, `SurfaceDesigner`, error page and loading pages, compiled with Next's SWC and rendered with `react-dom/server`; and behaviour tests with stand-in hooks (fix round 1).
- **`scripts/drill-editor-layout.js` + `drill:editor-layout` (new, not in `pnpm test`).** The browser drill. It needs a running harness and Chrome. It launches its own headless Chrome with a throwaway profile, refuses any `--base` that is not this machine, signs in with the harness's local test password (read from `.design-env`, never printed), measures, optionally saves screenshots, and exits 1 on any failed check. Options added in fix round 1: `--height`, `--classic-scrollbars`. No dependency was added: it uses Node's global `WebSocket`.

## Deviations from the spec

1. **Desktop is a real 1280px page, shrunk to fit and labelled.** "Device buttons set real widths": before, Desktop was `100%` of whatever space was left, so at 1024 the store would have drawn its tablet layout. Now the page always renders at 1280, so the store shows its desktop layout, and when the pane is narrower it is shrunk as a whole and the caption says by how much (71% at 1440, 59% at 1280, 56% at 1024). The acceptance allows "visibly scaled and labelled". **Owner's call:** 1280 or 1440 as "Desktop", and whether text shrunk to 56–71% is readable enough. No "actual size" toggle was added.
2. **The console navigation folds away completely on the designer, behind a menu button, rather than shrinking to the 64px icon rail.** With the rail, 1440 − 64 − 224 − 288 leaves 864px, and the 900px target at 1440 cannot be met with the spec's minimum tree and inspector widths. **Owner's call** whether that trade is right.
3. **Narrower side panes than before.** The tree is 224px (was 256) and the inspector 288px (was 320 on home, 352 on product and collection), just over the spec's 220 and 280, to give the preview the room. One visible cost: on the product and collection designers, the Template select's chosen text is cut off at about 221px ("Follow store default (Classic"). The open list shows it in full.
4. **Below 1024 the inspector goes under the preview.** The spec says nothing below 1280 except the drawer. Side by side, 1024 is the narrowest width where the preview keeps 600px.
5. **Only the designer routes get the full-width layout.** HomeEditor, PageEditor, Navigation and the rest keep the console layout until ED-02 brings them into one editor. `EDITOR_ROUTES` in `editorLayout.js` is the one list to extend; the error and loading pages follow it.
6. **The page header became a compact top bar.** The title is 16px, not the console's 24px. The breadcrumb shows only its first step ("Storefront ›"); from 1280 wide the store's name sits before it. **The description lines are now read to screen readers only, not shown, on all three designers:** home ("Compose the home page visually. Everything saves as a draft — publish from Publishing."), product and collection ("Pick a product [collection], preview its page, and set how it's presented. Everything saves as a draft — publish from Publishing."). The home save toast still says "Saved as a draft — publish from Publishing". Owner's call whether those sentences should stay visible (M7).
7. **The editor fills the window and the panes scroll on their own,** from 1024 wide up. Before, the whole page scrolled. Below 1024 the page scrolls as before.
8. **Two new script entries.** `test:editor-layout` joins the gate. `drill:editor-layout` is outside it, because it needs a server and a browser. The spec's planned Playwright runner (8.15) does not exist yet; the drill is a stopgap over Chrome's own protocol, with no new dependency, and should move to that runner when it lands.
9. **Fix round 1: picking a section in the Sections drawer closes it** (1024 to 1279 wide). The spec does not say. The cost: to move a section that is not already selected, the founder picks it (the drawer closes), reopens Sections, then uses Move up or down on it. Before, every pick needed Escape before the settings could be used. Owner's call (M10).

## Known limits

- **The store inside the frame, on the edge runtime, has still not been drawn on the harness.** Every frame shows the storefront's "Something went wrong" page: the storefront group is `runtime = "edge"`, and on file databases the edge reader logs `control plane unavailable`. This author made no runtime flip. **The reviewer did, temporarily (a local Node-runtime flip of `app/(storefront)/layout.js`, reverted, not committed), and reports:** B1 passes (clicking the hero, then a section, in the 71% frame at 1440 and the 56% frame at 1024 selects each in the inspector and outlines it); B2 passes (picking "New arrivals" in the drawer at 1024 outlines it and scrolls it into view); B3 passes on the announcement text (shown in about 1.0s, caption, frame width and inner width unchanged; on the hero title the seeded `hero-promise` experiment overrides the title in the storefront, so it cannot be shown there on this harness); B4 passes (the store inside reports `min-width: 1024` true and `innerWidth` 1280); B5 passes with the pairs region (the "Also on this page" card flashes into view at 76%; the harness product `glow-serum` renders no `pdp-modules` region). All of that ran on Node, not on the edge runtime. Still open: the same on edge (needs the harness fix), B3 on the hero title, B5 on a product with modules, and whether the store at 56–71% is readable (owner).
- **Close-on-pick was checked in the console only.** It does not depend on the frame, but B2 (highlight after a pick from the drawer) was the reviewer's run on round 0, before the drawer closed on a pick. Listed as a browser drill.
- **Thin margin at 1440.** The Desktop preview is 912px there, 12px over the 900 target. A wider tree or inspector would break it (M1). The default drill runs Chrome with `--hide-scrollbars`. With `--classic-scrollbars` (styled 15px scrollbars, an emulation of Windows and of a Mac set to always show them): see the results under Commands and results. A real classic-scrollbar machine was not used (owner's check M9).
- **Below 1024 the page scrolls,** so with classic scrollbars the preview loses about 15px (at 768, about 737px, still over 600).
- **Phones:** under 616px wide, the preview cannot keep 600px. ED-10 owns phones.
- **The tree drawer shows "Sections" twice:** the drawer's own title, then the tree's heading with Undo and Redo. Harmless, a little redundant.
- **Below 1280 the store's name, the StoreSwitcher and the Publishing unpublished-changes dot show only in the menu.** From 1280 the name is in the top bar; the StoreSwitcher and the dot are in the menu at every width. The dot is also computed when the layout renders, so it does not change after a save until the next navigation (true before this branch too). Owner's check M8.
- **Equivalent mutant, kept:** `EditorShell`'s initial `measure()` call and its `resize` listener add nothing where `ResizeObserver` exists (observing `document.body` fires on mount and on resize). They are kept as the path for a browser without `ResizeObserver`. No test can tell them apart in Chrome.
- **The behaviour tests use stand-in hooks, not React.** They call the components as plain functions and fake `useState`, `useRef` and `useEffect`, so they prove the handlers and state transitions, not the DOM, focus or real effects ordering. A React upgrade that changes how hooks are imported would need the stand-in updated. The browser drill remains the measured proof, and both should move to the planned runners (8.15).
- **Hydration warning on the product and collection designers, not caused by this branch.** `SurfaceDesigner` reads `sessionStorage` in a `useState` initializer, so the server renders "Pick a product" and the client renders the picked product. React logs "Hydration failed…" and re-renders on the client (the dev overlay's "1 Issue" in the product screenshots). Seen with the original `SurfaceDesigner.js` swapped back in too. Left alone, because it is not layout; reading the saved context in an effect would fix it.
- **The designer loading state was checked by rendered tests only,** not caught on screen during a real client-side navigation (it shows only while the server page loads, which is fast on the harness). Listed as a browser drill. Its title is "Designer" on all three routes, so on the product and collection designers the title changes when the page arrives.
- **Safari, iPad and touch** were not tried. The shell uses `dvh` units, `ResizeObserver`, `matchMedia(...).addEventListener`, `Element.closest` and the native `<dialog>`'s focus return, all in Safari 15.4 and later. See the owner's checks.
- **The render tests compile with SWC and stub** routing, toasts, pickers and the API client, the same stopgap as AU-05. They check markup, order and classes, not real layout.
- **`next build` was not run.** The dev server compiled all three designer routes, the error page, and the storefront pages it served.
- **Zoom, very tall windows and right-to-left** were not measured. Fix round 1 measured 720px-tall windows only with classic scrollbars; all other runs used 900px.
