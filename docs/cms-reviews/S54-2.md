# S54 review packet — Slice 2: composition foundation (audit D1)

**Work item (audit):** Slice 2 — versioned component registry, durable IDs,
templates/default assignments, shared renderer, compatibility reader.
**Acceptance gate:** Existing tenants render equivalent content; duplicated
sections remain independent.

## What was built
1. **Component registry** (lib/cms/registry.js): one versioned declaration
   per section type (home: collections/new/banner/rich_text · page:
   text/rich/image/faq) — identity, family, label, defaults, settings
   contract, data bindings. The validator sources kind lists and defaults
   from it; the data resolver reads its bindings; the next slice's editor
   controls render from the same declarations. Durable instance IDs
   (`sec_…`): ensureSectionIds keeps valid unique ids, re-mints duplicates,
   mints missing.
2. **Schema versions + lazy migration**: home_sections block v2 and
   PAGE_SCHEMA v3 stamp ids on legacy content at read — DETERMINISTICALLY
   (index-derived `sec_lN`; a random id at read would change the release
   snapshot hash every request). Saves persist real ids (validators stamp;
   editors round-trip them — PageEditor carries them as `pid` alongside its
   client keys and adopts server-minted ids right after save; duplicates
   drop the id so the server mints a fresh instance).
3. **Per-instance data + shared renderer**: lib/cms/section-data.js
   resolves data PER INSTANCE from registry bindings with identical queries
   batched and curated collections fetched once and sliced per instance —
   closing the audit's "repeated home sections overwrite each other's data"
   finding (each instance now honors its own limit). The homepage JSX moved
   verbatim into components/sections/HomeSections.js, keyed by instance id
   (index fallback for id-less legacy live snapshots), `#new` anchor on the
   first newest-products section; shoppers and preview share it by
   construction.
4. **Diff/envelope compatibility**: content envelope v3; releaseDiff strips
   section ids before comparing (identity ≠ shopper-visible change — the
   lazy upgrade can't fake "unpublished changes"), and the one-time
   "Publishing upgrade" item covers v<3 live releases.
5. **Tenant-saved templates** (the slice's template deliverable, scoped to
   what renders today): cms_templates (migration 0014) + templates-store —
   validated section compositions per family; instantiation returns an
   INDEPENDENT copy with fresh ids (explicit copy semantics; linked shared
   sections remain future work, stated). Wired through the one-op CMS API
   (listTemplates/useTemplate reads · saveTemplate/deleteTemplate writes,
   same authorization discipline), with "Save as template" and a "Your
   templates" group in the page editor's create flow. Templates are
   authoring assets — deliberately NOT in release snapshots.
   Template→rendering assignment (family defaults choosing LAYOUTS) is NOT
   claimed: today's families share one renderer; assignment lands with the
   editor slice where distinct layouts exist.
