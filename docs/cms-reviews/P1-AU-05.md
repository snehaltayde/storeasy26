## The bug, reproduced first

✗ paragraphs with no heading survive save and reload (the reported data loss)
   reloaded form: expected [{"kind":"text","heading":"","text":"First paragraph.\n\nSecond paragraph."}], got []
✗ the storefront reader gets the paragraphs and an empty heading

So the save logged success and stored `[]`. Whole run: `4 passed, 19 failed`. The suite had 23 tests then; the registry test came later.

## Fix round 1

An independent reviewer found one blocker and four minor items. All five were checked against the code and all were right.

- **Blocker: ordinary words typed into FAQ answers and rich sections were lost, with a 200.** Fixed: the save is now refused and the message quotes the words. See "Words the sanitizer would remove".
- **The suite did not run the components.** Fixed: `ContentPage` now renders in the suite, and `PageEditor`'s load and save logic runs on stand-in hooks. Load mapping moved to `formSections` in `pageSections.js`.
- **The http image link message used internal wording.** Reworded. The reviewer's suggested text contained `https://`, which the suite's own plain-words rule forbids, so it reads: `section N: this image link isn't secure. Use a link that starts with https, or choose an image from your library.`
- **A section holding only a zero-width character counted as content.** Fixed for the emptiness check only. Stored words keep these characters, because Indian scripts and emoji need them to display correctly.
- **Each save added another `rel` to a link with a target.** Fixed in `sanitizeAttrs`. A row that already holds duplicates shrinks on its next save. Round 2 changed how the words are merged.

### Words the sanitizer would remove

`validatePageSections` now compares what the founder typed with what the sanitizer returns, using `wordsLostBySanitizing` in `lib/sanitize.js`. Any visible words missing from the result refuse the whole save with the row untouched, and the words stay in the form.

Before, through the real handler (reviewer's probe). Now, exact message:

| Typed | Before | Now |
|---|---|---|
| `Free on orders <500 and >100 rupees.` | 200, stored `Free on orders 100 rupees.` | 422 `section 1, question 1: saving would lose these words: "<500 and >". This usually comes from < or > signs. Reword them or remove them, then save again.` |
| `Write to Priya <priya@store.com> any day.` | 200, stored `Write to Priya  any day.` | 422, quotes `<priya@store.com>` |
| `<p>Keep it at a<b and c>d always.</p>` | 200, stored `<p>Keep it at a<b>d always.</p>` | 422, quotes `<b and c>` |
| `<p>Hello</p><noscript>Important founder words</noscript>` | 200, stored `<p>Hello</p>` | 422, quotes `Important founder words` |

Refusal was chosen over encoding the stray `<` in the sanitizer because encoding does not help `<b and c>` or `<priya@store.com>`, which parse as tags. It would also change what every other sanitizer caller stores.

What counts as words: anything between `<` and `>` that is not real HTML. Real HTML means a known HTML tag name, or a Word tag (prefix `o`, `w`, `v`, `m`, `st1` or `x`, then letters and hyphens), with well-formed attributes. A bare attribute must be on the known list or start with `data-` or `aria-`. A tag the sanitizer strips counts as words when it has no attributes and nothing closes it later, except `col` and `wbr`, which real HTML holds bare. Text inside `noscript`, `svg`, `math` and `object` counts, and so does everything after a `script`, `style`, `iframe` or `template` that is never closed, because the sanitizer drops it all.

What still saves, because no visible word or link address is lost: scripts, styles, closed iframes, comments, event handlers, `javascript:` and `vbscript:` addresses, unknown attributes. Those keep AU-06's notice.

## Fix round 2

A second independent review found one blocker, one major and six minor items. All eight were checked against the code. All were right, and the two main ones reproduced with the reviewer's probes through the real handler.

**Blocker: ordinary words still vanished with a 200.** The round 1 check treated any name with a colon as a tag, any attribute with a hyphen as markup, and any real tag name as markup. Round 1's status for negative 3 overclaimed. Fixed in `isMarkup` and `visibleText`, and all of these are now in the stray brackets table.

| Typed, both fields | Before, 200 and stored | Now, 422 quoting |
|---|---|---|
| `Call <tel:9876543210> now.` | `Call  now.` | `<tel:9876543210>` |
| `<Price:500> only.` | ` only.` | `<Price:500>` |
| `Use <code:SAVE10> at checkout.` | `Use <code> at checkout.` | `<code:SAVE10>` |
| `Save <b free-shipping> today.` | `Save <b> today.` | `<b free-shipping>` |
| `Click the <link> below.` | `Click the  below.` | `<link>` |
| `Send your <address> and <time>.` | `Send your  and .` | `<address> and <time>` |

`<center>x</center>`, `<time>x</time>`, Word's `<o:p>` and `<st1:country-region w:st="on">`, and `<p data-sale aria-hidden>` still save.

**Major: a link or image address the founder typed was removed with a 200.** `tel:`, `sms:`, `whatsapp:` and addresses with no scheme are not on the sanitizer's list, so the link went dead and the form went clean. These are not unsafe, and round 1's "unsafe link" wording understated it. Now refused:

```
section 1: saving would lose this link or image address: "tel:+919876543210". It needs to start with https or a slash (/). Change it or remove it, then save again.
```

`addressesLostBySanitizing` in `lib/sanitize.js` reports them from inside the same pass the sanitizer runs, so it cannot disagree with what gets removed, and `sanitizeHtml` returns the same text as before. Only `<a href>` and `<img src>` count, since those are the attributes the sanitizer keeps. An address that only runs code stays AU-06's notice. A pasted `data:` image is refused, because the picture would otherwise disappear. `SAFE_URL` is unchanged, so **a click-to-call link still cannot be saved**. See deviation 10 for the owner's decision.

**Minor items.**
- **Packet overclaim on old rows.** Corrected. See "Rows saved earlier" in the limits. A new test pins the reviewer's row.
- **Invisible characters.** `isBlank` now ignores all format characters, combining marks and control characters, plus blank Braille and the Hangul fillers. The suite checks 21 kinds. This is for the check only, as before. Stored text is untouched.
- **Empty markup counted as content.** `<p></p>`, `<br>`, `<p>&nbsp;</p>`, `<div></div>` and the like are now refused in rich sections and FAQ answers. A picture or a dividing line alone still counts.
- **`rel` words were replaced.** They are now merged. `nofollow` and `sponsored` stay, `opener` goes, and `noopener noreferrer` appears once. `<a rel="nofollow" href="/x" target="_blank">` becomes `rel="nofollow noopener noreferrer"`. Sanitizing again changes nothing.
- **Three copy changes had no test.** The source guard now covers the copy about empty sections, the `Heading (optional)` placeholder and the badge number.
- **The `test:shopify-push` flake was understated.** Corrected in Test results. Not fixed here.

Where this differs from the reviewer's suggestions: a Word tag's local name may hold hyphens, because Word writes `st1:country-region`. `col` and `wbr` are exempt from the lone-tag rule. `<hr>` counts as content next to `<img>`. `isBlank` also ignores control characters. The old-row finding was handled by narrowing the claim, because measuring the limit on what was typed only moves the refusal to the save after.

## What changed

- `components/admin/cms/pageSections.js` (new): the form conversions, moved out of `PageEditor.js` so a plain node test runs the same code. It has no JSX and no imports. `sectionsPayload` sends every section and filters nothing. `editEmpty` now means nothing typed in any field; only the Save as template button's enabled state uses it.
- `components/admin/cms/PageEditor.js`: page Save and Save as template both use `sectionsPayload`. Copy no longer says empty sections are dropped. The text heading placeholder no longer says required. Each section badge shows its number, because refusals say "section 3".
- `lib/cms/store.js` `validatePageSections`: a text section needs a heading or at least one paragraph. Whitespace does not count. A paragraph value that is not a list is refused, not discarded. Blank rich and image sections get plain messages, and a rich section or FAQ answer holding only empty tags counts as blank. Over-limit text is refused, not cut (see deviations).
- `lib/cms/registry.js`: the text declaration no longer marks `heading` required.
- `components/ContentPage.js`: the text heading renders only when there is one, the same line the rich branch already used.

The editor's `setSnap` call is unchanged. It only runs on success, and the payload now holds everything, so clean means stored. The later id adoption (`fresh.page.sections[i]`) also lines up now. Before, a dropped section shifted those positions, and shifted the number in server messages.

## Deviations from the spec

9. **The suite compiles with Next's SWC instead of the runner in spec 8.15.** It is a stopgap with no new dependency. When the JSX runner lands, the render tests and drills D1 and D2 should move to it.
10. **Link and image addresses are refused here, not left to AU-06. The owner should confirm this and decide on phone links.** A founder who types a `tel:`, `sms:`, `whatsapp:`, scheme-less or relative address now gets a refusal, where before the link silently died. Adding `tel:` and `sms:` is one line and both are safe, but it widens the sanitizer's allowlist, so it is the owner's call. WhatsApp has an https form (`wa.me`) that already works. Addresses inside elements the sanitizer removes (`iframe`, `video`) stay with AU-06.
11. **Empty markup is refused as blank.** This is older than the branch and loses nothing, so it is not strictly negative 3. It was cheap, and it stops an empty block being published. A section already stored that way is refused on its next save until the founder removes it or adds content.
