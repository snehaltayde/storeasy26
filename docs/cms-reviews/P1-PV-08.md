## Fix round 1

An independent reviewer found two blocking problems and ten smaller items. I checked each against the code. Both blocking problems were right, and so were the smaller items. Each blocking problem was reproduced before the fix: by a test, and in the browser on the `da7617f` code.

### Blocking 1: once the preview cookie lapsed, the founder saw variant b in the Designer and was counted

**The review was right, and the packet was wrong in four places.** `app/api/preview/route.js:45` sets the preview cookie's Max-Age to the token's remaining life (1 hour). The browser deletes the cookie at that moment; I measured the cookie's expiry against the token's at -0.1 to -0.8 s. The Designer stays open and signed in (the console cookie lives 7 days), and its next "Refresh preview" or Save reloads `/` with no preview cookie. At `da7617f` that page treated the founder as a shopper: it bucketed them, showed variant b, and pinged `/api/exp`, which recorded the exposure. Their orders converted, because `conversionUnit` only looked for the preview cookie. The old packet said the opposite in Deviation 1, the expired-session Known limit, owner check 5 and acceptance row 2. The unit test's "expired" cookie was one no browser sends: it is deleted at expiry.

**Reproduced first.**

**The fix: a browser signed in to the console is the founder's, preview or not.**
- `lib/experiments.js`: `signedInToConsole(jar)` is true when the request carries the merchant console cookie (`_admin`) or the operator cookie (`_platform`). Both are set with path `/`, so the storefront, `/api/exp` and `/api/checkout` already receive them. It checks presence only, like the preview cookie: only sign-in sets one, so a stale or hand-made one only keeps its own holder out of the test. `isFounderRequest(request)` is a preview cookie or a console cookie. `conversionUnit` returns `null` for either. `CONSOLE_COOKIES` names the two cookies (not imported, so the storefront page doesn't load the console's sign-in code); a test checks they match `ADMIN_COOKIE` and `PLATFORM_COOKIE`.
- `heroVariantFor(…, { preview, founder })`: with `founder`, outside a preview, it returns the hero it was given and no assignment, so nothing is shown from the test and nothing pings. It returns no note: the note needs a valid preview, so a hand-made console cookie never shows a test's name.
- `app/(storefront)/page.js` reads the cookie jar once and passes `{ preview: src.preview, founder }`.
- `app/api/exp/route.js` refuses with `isFounderRequest` before anything is read or written.

**What the founder sees now when the preview lapses:** the Designer frame shows the live store's hero ("Skin first. Makeup second." on the harness), not variant b, with no note. It can't show their draft, because drafts need a valid preview token; renewing that is PV-04's. The Designer still reads "Connecting…". Nothing is counted, and their orders convert nothing.

After the fix ([lapsed-designer](drills/PV-08/lapsed-designer.png)): the frame shows the live hero both times, 0 `POST /api/exp`, a ping sent by hand from the frame answers `recorded:false`, no exposure row for the unit, exposures in all 53 → 53. The COD order (`DES-A7BFE177`) converts nothing. The same under the production build.

## What was built

- **`lib/experiments.js`**
  - `heroVariantFor(experiment, hero, unitId, { preview, founder })`. In a preview it returns the founder's hero untouched, `assignment: null` (so nothing pings) and `notice: { slug, name, section: "hero" }`. Signed in but out of preview (`founder`), it returns the hero untouched and no assignment, and no note. Nothing is picked in either case, not even a bucket. With neither, the code path is the `8968db3` one, unchanged.
  - `isPreviewRequest(request)`: true when the request carries a `_preview` cookie, whatever its value.
  - `CONSOLE_COOKIES`, `signedInToConsole(jar)`, `isFounderRequest(request)` (fix round 1): a console cookie (`_admin` or `_platform`) present, and "a preview cookie or a console cookie".
  - `conversionUnit(request)`: `null` for the founder's browser (`isFounderRequest`), otherwise the `_unit` cookie.
  - `runningTestsBySection()`: `{ hero: { slug, name } }` for the console's notes. Running tests only; paused and completed ones are left out.
  - `TEST_SECTION`: which storefront section (its `data-sec`) each test target changes. Only `hero` exists.
- **`app/(storefront)/page.js`**: reads `contentSource()` in the same `tfetch` pass (React-cached, so no extra read) and passes `{ preview: src.preview, founder }`, where `founder` comes from the request's cookies. The ping still mounts only with an assignment, which the founder's browser never has. `<ExperimentNote>` renders inside `[data-sec="hero"]` when there is a notice.
- **`components/preview/ExperimentNote.js`** (new, no hooks, edge-safe): the preview's note, in the same purple as the "Draft preview" bar: *A test is running on this section: "Hero promise test". Some visitors see a different version; the preview shows yours. See the test*. The link goes to the test's row in the console (`target="_top"`); inside the Designer the preview bridge turns a click in the hero into selecting it, as before.
- **`app/api/exp/route.js`**: a request from the founder's browser (`isFounderRequest`) gets `{ ok: true, recorded: false }` before anything is read or written.
- **`app/api/checkout/route.js`**: both conversion units (COD, and online payment after verification) come from `conversionUnit(request)`, so an order from the founder's browser converts nothing.
- **Designer** (`components/admin/cms/Designer.js`, new `components/admin/cms/TestRunningNote.js`): when a test runs on the hero, its settings open with an info banner, *A test is running on this section. It's called "Hero promise test". Some visitors see a different version; the preview shows yours. See the test*. "See the test" opens the test's row in a new tab, so unsaved edits stay (fix round 1). The tree's Hero row carries a "Test running" mark. The mark is the row's description (`aria-describedby`), so the button's accessible name stays "Hero"; its visible text (`innerText`) is "Hero" then "Test running" on a second line.
- **Designer page** (`app/(console)/admin/(authed)/storefront/designer/page.js`): loads `runningTestsBySection()` beside the view; a failed read costs only the note.
- **Experiments screen** (`components/admin/ExperimentsAdmin.js`): each row has `id="exp-row-<slug>"`, the anchor both notes link to. No per-test page exists, so the link opens the list at that row. `exp-row-` keeps it apart from the form's own ids (`exp-slug`, `exp-name`, …).
- **Tests and drills**: `scripts/test-preview-experiments.js` (`test:preview-experiments`), `scripts/drills/p1/pv08.mjs` (parts `designer`, `preview-tab`, `shopper`, `conversion`, and from fix round 1 `lapsed` and `lapsed-order`). `scripts/test-copy.js`'s home-page render gets the two new imports stubbed. `scripts/drills/p1/harness.mjs`: finding 1's two preview checks are plain checks now (they pass and must keep passing); the signed-out check stays known, relabelled, because a running test *should* show variant b to some shoppers. `scripts/drills/p1/doc04.mjs`: the tree list reads each row's first line (fix round 1).

### Every place a variant is chosen or applied, and what gates it

Searched `app/`, `lib/` and `components/` for `assignVariant`, `heroVariantFor`, `runningExperimentFor`, `ExperimentPing`, `/api/exp`, `recordExposure`, `recordConversions` and raw `_unit` reads. The guard test pins this exact list, so a new surface test, module test or commerce experiment fails it until it is gated and listed.

| Place | Kind | Gate |
|---|---|---|
| `lib/experiments.js` `assignVariant` | picks a bucket | only called by `heroVariantFor` (after its preview and founder returns) and `recordExposure` (behind the route's gate) |
| `app/(storefront)/page.js` → `heroVariantFor` | applies the hero variant | `{ preview: src.preview, founder }` |
| `app/(storefront)/page.js` → `<ExperimentPing>` | exposure ping (client) | mounts only with an assignment; the founder's browser has none |
| `app/api/exp/route.js` → `recordExposure` | exposure write | `isFounderRequest` refuses first |
| `app/api/checkout/route.js` → `recordConversions` (twice) | conversion write | `conversionUnit(request)` |
| Offers, bundles, quizzes, upsells, surfaces, sections | none | no experiment code; `TARGET_KINDS` is `["hero"]` only |
| Product and collection designer previews | none | no experiment is served on those pages |

## Deviations

- **The founder's browser is "a preview cookie or a console cookie", and only a valid preview token makes a preview.** The page shows the founder's own content (and the note) only for a valid, tenant-bound preview token (the existing rule, `contentSource`). `/api/exp` and checkout refuse to count any request that carries a `_preview`, `_admin` or `_platform` cookie, valid or not, and the home page applies no variant to a browser with a console cookie. Only the console sets these cookies, so a stale or hand-made one only keeps its own holder out of the test; a shopper can't be affected. When the preview lapses (the browser deletes the cookie with the token, after 1 hour), the founder is still signed in: the Designer frame then shows the live hero, with no variant and no note, and nothing is counted, their orders included. Tested both ways.
- **A browser signed in to the console never sees a test's other version, on the live store too, and is never counted** (fix round 1). This is wider than the brief, which named preview views. It was the simplest way to cover a lapsed preview, and it also keeps the founder's own browsing and test orders out of the results. To see what a shopper sees, the founder uses a private window. Owner decision: manual check 5.
- **The tree's "Test running" mark** is beyond the brief, which asked for the note beside the settings. It shows the test before the founder selects the hero. It is the row's description, so the button's accessible name stays "Hero". Its visible text gains a second line, which broke one batch B drill that read the text (`doc04 overview`, fixed in the drill).
- **"See the test" in the Designer opens a new tab**, so unsaved edits stay (fix round 1). The preview note's link opens in the top window (`target="_top"`), as before.
- **The link goes to the test's row on the Experiments list**, since there is no page per test. Rows gained `id="exp-row-<slug>"`.
- **Conversions are gated in `app/api/checkout/route.js`**, which the pending payment branch rewrites (see Merge notes).
- **The Home page editor** (`/admin/storefront/home`), which also edits the hero, shows no note. The brief named the Designer; that screen has no preview pane. See Known limits.
- **The preview note uses the "Draft preview" bar's purple**, not the store's tokens: it is preview chrome, and it must read on any brand.
- **`scripts/drills/p1/harness.mjs` changed** (batch B's drill): two finding 1 known markers removed, one relabelled. **`scripts/drills/p1/doc04.mjs` changed** (fix round 1): its tree list reads each row's first line.
- **`scripts/test-copy.js` changed**: its home-page render stubs the two new imports (`ExperimentNote` renders nothing for shoppers; `contentSource` says not a preview). Its `cookies()` stand-in has no console cookie, so the page treats it as a shopper.

## Known limits

- **When the preview lapses, the Designer stops showing the founder's edits.** The preview cookie lives as long as its token, 1 hour, and the browser then deletes it. The Designer, still open, keeps saying "Connecting…" and its frame shows the live store's hero, not the draft, until the founder reloads the Designer (which mints a new preview). No variant shows and nothing is counted (fix round 1). Renewing the session is PV-04's. Only checked by dropping the cookie by hand, not by waiting an hour.
- **A signed-in founder never sees a test's other version on their own store.** Their browser isn't bucketed or counted anywhere on the store, live pages included. To see what shoppers see they need a private window. Owner decision: manual check 5.
- **The console cookie is checked for presence, not validity.** A stale (revoked session) or hand-made `_admin` or `_platform` cookie keeps that browser out of the test; it sees the live hero and isn't counted. Sign-out deletes `_admin`.
- **Sign-out doesn't end a preview** (older than PV-08). The preview cookie survives sign-out until its hour ends or "Exit preview" clears it, so that browser keeps seeing drafts and stays uncounted for up to an hour.
- **One experiment target exists (hero).** The gate is per serving place: a new target (a section, a module, an offer) needs its own `{ preview, founder }` gate and note. The guard test and `TEST_SECTION` fail or point at that, but they can't write the gate.
- **The Designer learns which tests run when it loads.** A test started, paused or completed while the Designer is open keeps the old note and tree mark until a reload. The preview frame's note is always current (it renders per request). The reviewer measured this on `da7617f`: after pausing and "Refresh preview" the frame had no note and the founder's title; the tree's mark stayed until the Designer was reloaded; resuming and reloading brought both back.
- **Paused tests** serve nobody, show no note and have no Designer mark (tested since fix round 1; drilled by the reviewer).
- **"Publishing →" and the Designer's tabs still lose unsaved edits**, as before PV-08: they are in-app links, and `useDirtyGuard` only covers leaving the page. Only "See the test" changed (it opens a new tab).
- **A client-approval link shows the note too.** `app/(console)/approve/[token]/page.js` gives the client a preview, and its hero shows "A test is running on this section…" with "See the test", a console link the client may not be able to open (it asks them to sign in). Owner decision: manual check 6.
- **The Home page editor shows no note**, though it edits the same hero. Its own "Preview" opens a preview tab, which does show the note.
- **Online payment conversions are proven by unit test and source guard only.** The harness has no Razorpay keys, so the browser drill covers COD; the route itself can't run in plain Node (Next's `after()` needs a request scope).
- **A shopper who opens a preview link becomes uncounted.** Only founders get preview cookies, but a founder who later browses as a shopper in the same browser stays uncounted until the cookie expires (it lives as long as the token, 1 hour) or "Exit preview" clears it. Since fix round 1 the same holds while they stay signed in to the console.
- **A shopper with a stale or forged preview cookie sees the live page (variant b if bucketed into it) and isn't counted** (the reviewer measured `recorded:false`). A stale one only happens after the preview secret changes, or within the 60-second minimum Max-Age when a token had less than a minute left.
- **Chrome only, headless, on macOS.** `next dev` and a production build (`next start`) both ran here. No Safari, no phone, no hosting.
- **The rendered tests stub the page's heavy children** (`HomeSections`, `EmptyCatalog`, the marketing home) and replace `ExperimentPing` with a marker, since a server render never runs its effect. The browser drill is the proof that the real ping does or doesn't fire.
- **`next/headers` is a stand-in in the rendered tests**: one request jar that the real resolver, tenant lookup and page all read. It is not Next's request scope.
- **The drill's `_unit` workaround** depends on the runner's cookie reuse staying as it is; `setUnit` throws if the browser's unit isn't the one asked for.
