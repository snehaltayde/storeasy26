# UI

This project has its own look. It does not imitate another product and does not ship a
component library's default styling.

This page covers the **consoles** (`/admin`, `/platform`, onboarding). They are built from shadcn/ui components copied into `components/ui/` and restyled with the tokens below. The **storefront** is not covered here: it is drawn from each store's own brand tokens (`app/globals.css`, `--sf-*`, the design document) and never uses shadcn or these console tokens.

## Type

- **Families:** Geist Sans for everything (already loaded by `app/(console)/layout.js`); Geist Mono for numbers that line up (money in tables, order numbers, ids, counts).
- **Scale (rem):** 0.75 caption · 0.8125 small and table text · 0.875 body (the console default) · 1 emphasised body · 1.125 section title · 1.375 page title · 1.75 onboarding headline only.
- **Weights:** 400 body, 500 labels, buttons and table headers, 600 page and section titles. No 700+.
- **Rules:** sentence case everywhere; numbers in tables are right-aligned and tabular; uppercase only for tiny status labels, with 0.04em letter spacing.

## Color

Tokens live as CSS variables in `app/console.css` under `.console` (light) and `.console.dark` (dark) and are mapped to shadcn's names (`--background`, `--primary`, `--sidebar-*`, …). Components use tokens, never raw values.

- **Where `.console` goes:** on the console root `<body>`, not `<html>`: Radix portals (menus, sheets, tooltips) mount into `body`, and on `<html>` the storefront's later `:root { --background }` in `app/globals.css` would win.
- **Dark mode is class-based:** `.console.dark` on the same `<body>`. The `dark:` variant matches only inside `.console.dark`, never on the storefront. There is no toggle yet.
- **Old screens (`data-legacy`):** `--c-surface`, `--c-border`, `--c-accent`, the four status names, `--primary` and `--ring` are also the old `[data-console]` tokens. Every old screen sits in a `data-legacy` region (`<div data-legacy className="contents">`, no box of its own): the shell's `main`, `admin/(auth)/layout.js`, `platform/layout.js`, the roots of `app/(console)/error.js` and `not-found.js`, and the Toast viewport. In `app/console.css`, `.console [data-legacy]` shares the old block with `[data-console]`, restores `globals.css`'s `--background`/`--foreground`, the old line height and text colour, and keeps borders at `currentcolor`, so an old screen looks exactly as before (`pnpm drill:console-styles` proves it). New UI is never put inside a `data-legacy` region; the Phase 2 line that retires the old screens removes the wrapper.
- **Warning as text:** measured (WCAG 2.x, oklch → sRGB): light `--c-warning` is 2.97:1 on `--c-surface`, 2.85:1 on `--c-bg`, 2.66:1 on `--c-sunken`, so it is for fills, borders and icons only. Warning *text* uses `--c-warning-text` (light 5.71 / 5.48 / 5.11:1, and 4.77:1 on a 10% warning tint; dark keeps the warning value, 9.3:1 or more). In classes: `text-warning-text`.
- **Measured contrast of the other text tokens:** `--c-muted` light 6.00 / 5.77 / 5.38:1 on surface / bg / sunken, dark 6.63 / 7.15 / 7.36:1; success, danger and info are 4.65:1 or more on every light surface. The primary button's hover darkens the accent (mix 15% `--foreground`) instead of fading it: `bg-primary/80` would drop white text to about 5.4:1 and lightens towards the page.

## Spacing and layout

- **Scale (px):** 4, 8, 12, 16, 24, 32, 48, 64. Nothing in between.
- **Shell:** a 240px sidebar (collapses to icons below 1024px, to a sheet below 768px), a 56px top bar with the store switcher and the account menu, content max width 1200px with 24px gutters (16px on phones).
- **Onboarding:** no sidebar; one centred column, max width 640px, with the step list on the left from 1024px up. The current step's panel is the page's only card and holds its one primary action ("Next: …", "Go to <the step it waits for>" on a blocked step, "Go to your dashboard" once all four are done); the welcome block above it is flat, like the signup screens. Every step is new UI (Import since line 5, Brand since line 6), so no step has an old-screen tray. **A wide step** (its panel sets `wide`; Brand since line 6) takes the whole row beside the step list, up to 1200px (the shell's onboarding `main` is 1200px from 1024px up); the Welcome card and the step header stay 640px. Brand puts its form and a live preview of the home page side by side from 1024px (the preview sticky); narrower, a sticky "Preview" button opens it as a bottom sheet (Esc and a close button close it). There is one preview element, moved between the column and the sheet by CSS at 1024px, so a resize never mints a second preview session. The preview frame says the look hello: no section picking, no preview bar; unsaved choices are drawn by a message to the frame, never a write.
- **Density:** tables use 40px rows on desktop and 48px on touch; forms use one column below 768px and at most two above. Menu items and sidebar links grow to at least 40px on a coarse pointer (`pointer-coarse:`).
- **The merchant shell (Phase 0 line 8):** `components/admin/shell/AdminShell.js`, built from `components/ui` only. A "Skip to content" link first; the sidebar (`cookiePath="/admin"`, the `sidebar_state` cookie read on the server for `defaultOpen`) with the Storeasy mark (the lime logo) and the nav groups Overview, Orders, Catalog, Storefront, Growth, Store, each item an icon, a label and a badge where one applies (open returns on Orders, setup progress on Setup, a warning dot on Publishing); the current item gets `aria-current="page"` by longest path prefix. The 56px top bar holds the sidebar toggle, the store switcher (DropdownMenu radio group of the caller's own stores, always shown, plus "Open storefront"), the read-only label for support ("Read-only access", or "Platform support access · read-only" for an operator) and the account menu (name, email, role in plain words, a read-only note for support, Sign out). The support-access and incident notices sit at the top of the content area. The nav model is `lib/admin/nav.js`: the server sends only the items `roleAllows`; hidden, never disabled. Group labels are sentence case. Editor routes keep the shell out of the way: no sidebar or top bar, the nav opens in a sheet (`useConsoleNav`, `ConsolePageFrame`).
- **Sidebar behaviour:** expanded at 1024px and up (the founder's toggle and `⌘B` persist in a cookie); 768–1023px it opens as icons with tooltips, and the toggle expands it for that visit only; below 768px it is a sheet. The 56px top bar is the shell's (line 8), not a `components/ui` part.
- **Motion:** every transition and animation in `components/ui` stops under `prefers-reduced-motion` (`motion-reduce:` / `motion-safe:`).
- **Radius:** 6px controls, 10px cards and dialogs, full for pills and avatars. In classes: `rounded-md` (6px, Tailwind's own) for controls, `rounded-card` (10px, `app/console.css`) for cards, popovers, menus, sheets and dialogs (tooltips are small labels and stay `rounded-md`), `rounded-full` for pills and avatars. The `--radius-*` scale is not overridden. Shadows: `shadow-card` at rest, `shadow-overlay` for menus and sheets.

## Components

- **From shadcn, restyled:** Button, Input, Textarea, Select, Checkbox, Switch, RadioGroup, Label, Form (react-hook-form + zod for validation messages), Dialog, AlertDialog (every destructive action), Sheet, DropdownMenu, Command (store switcher and search), Tabs, Table, Badge, Card, Tooltip, Popover, Skeleton, Separator, Sonner toasts, Sidebar.
- **Our own, built from those:** `PageHeader` (title, description, primary action), `StatusBadge` (maps a domain status to a status colour and plain word), `EmptyState` (one sentence and one action), `DataTable` (sort, filter, paginate, row actions), `StepList` (onboarding progress), `MoneyCell`, `RoleGate` (hides a control the role cannot use and shows the reason on hover).
- **Installed so far (Phase 0 line 7):** Button, Input, Separator, Skeleton, Tooltip, Sheet, DropdownMenu, Avatar, Sidebar (plus the `use-mobile` hook and `cn`), in `components/ui/`. Dialog arrived with Phase 1 line 7 (onboarding step 4's "Open your store"); RadioGroup with Phase 1 line 6 (onboarding step 3's colours). The rest of the list above arrives with the first screen that needs it. **Command** (the store switcher and `⌘K`) is deferred with `cmdk`; Sonner and Form (react-hook-form + zod) are deferred too. How to add one: `components/ui/README.md` (generate in a scratch project, never run the shadcn CLI in this repo). **Phase 1 line 8 adds** Table, Badge (plus status tones `success`, `warning`, `danger`, `info`, `muted`: a tint with the status colour as text; warning text is `text-warning-text`), Textarea, Label and AlertDialog (shadcn 4.23.0), first used by the operator's `/platform/onboarding` screen. That screen is the first operator screen on `components/ui`: `app/(console)/platform/layout.js` is a pass-through and the old operator screens carry their own `data-legacy` region (`page.js`, `loading.js`, `error.js`).
- **Phase 2 line 0 adds** Card, Tabs, Select, Switch, Checkbox and Popover to `components/ui/` (shadcn 4.23.0, restyled), and our own parts in **`components/kit/`**, built on `components/ui` only (plus `lib/format.js` and `lib/platform/authz.js`): `page-header.js` (`PageHeader`: title, description, breadcrumb, actions), `status-badge.js` (`StatusBadge`: plain words and tones for order, offer, bundle, media and sync states; `offerState()`), `empty-state.js` (`EmptyState`), `money-cell.js` (`MoneyCell`: `formatMoney`, mono, right-aligned), `role-gate.js` (`RoleGate`: hides a control, or shows it `aria-disabled` with the reason in a tooltip, still focusable) and `data-table.js` (`DataTable`: columns, row link, row actions slot, skeleton rows, empty state, a sticky header in a height-capped scroll box, 40px rows (48px on touch), truncation with a tooltip, a "1–50 of N" footer with Previous/Next or "Load more"; sorting and filtering come from the server through props, no TanStack). Tested by `pnpm test:console-kit`. A page on the new UI is listed in `lib/admin/new-ui-routes.js`: the shell then puts it straight into `main` (no `data-legacy` region; the notices keep their own), and support's stray-control rule covers all of `main`, so a read control on such a page (a search box, a filter, a row link, Next) carries `data-read-control` on the control itself (never an ancestor), never on a submit button or inside a form that is not `method="get"`, and outside `components/kit/` only with a reasoned row in `scripts/support/read-controls.js`; the kit's own reads already do. A blocked write passes only as RoleGate renders it (`aria-disabled="true"` with `data-role-gate="disabled"`) or natively `disabled`. `MoneyCell` has no default currency: pass the store's.
- **When to add one:** only when the same arrangement appears on three screens. Otherwise compose in the screen.
- **Words:** plain sentences, no error codes on screen, every refusal says what to do next. Buttons say what they do ("Publish home page", not "Submit").

## States

Every screen is designed for: loading, empty, error, populated, crowded, and the
least-trusted role's view where that role can reach it. Keyboard behaviour is part of the
design.

- **Loading:** Skeletons shaped like the content, never a lone spinner for more than a button.
- **Empty:** `EmptyState` with the next step; on a brand-new store it points back to onboarding.
- **Error:** what went wrong in plain words, a "Try again", and nothing already typed is lost.
- **Crowded:** tables paginate at 50 rows and keep the header and actions visible; long names truncate with the full name in a tooltip.
- **Support role:** write controls are hidden or disabled with the reason; the page never shows a button that will be refused.
- **Keyboard:** every action reachable by Tab, visible focus ring in `--c-accent`, Esc closes dialogs and sheets, `⌘K` opens the command menu.

### Dashboard

### Orders

`/admin/orders` and `/admin/orders/[id]` (Phase 2 line 2), in `components/admin/orders/`.

- **List:** the address holds the state: `?status=` (tabs All, Pending payment, COD pending, Paid, Pushing, Pushed, Push failed, Cancelled, each with its count), `?payment=cod|online`, `?q=`, and `?view=returns` for the Returns tab. Every filter is a link and the search is a `method="get"` form, so each is a marked read and support can use them all. Counts follow the payment and search filters, so a tab's count is what it shows. Columns: order id (mono, the row link), placed (the store's timezone), customer ("Hidden for support" for support), payment in words, status (`StatusBadge`), total (`MoneyCell`, the order's currency), Shopify (the Shopify number, or the push error truncated with a tooltip). 50 rows, then "Load more" fetches the next page with the opaque cursor; a failed load keeps the rows and offers Try again. Empty: "No orders yet", or "No orders match" with Clear filters. Support's search box says "Order id": it searches ids only.
- **Returns tab:** open requests (status, order link, the shopper's reason in quotes, requested date, amount), then resolved ones. Approve, Mark received and Reject open an AlertDialog with an optional note; a refusal stays in the dialog with the note. Support sees the status only (the decisions are hidden). The banner line says approving moves no money.
- **Order page:** the title row has the id with Copy, the status, and Shopify's financial and fulfilment states; the actions are Push to Shopify (only while the order can be pushed), Refresh from Shopify (only once pushed) and Cancel order (only when the order can be cancelled), each for owner and admin only and hidden otherwise. A failed push shows its error above the cards. Cards: Customer (support: "Hidden for support", no fields), Payment and sync (with View in Shopify once pushed), Items (each line, the Shopify title and SKU line where the shopper saw another title, totals with the coupon, shipping and refunds), Shipments with tracking links, Refunds, Timeline (state changes in words). Every answer is a toast in plain words, then the page refreshes.
- **Cancel dialog:** a reason (up to 200 characters, with a counter); for a captured payment, the Razorpay refund id with the words to refund in Razorpay first, and the confirm stays disabled until it is filled. Each refusal is shown in the dialog in words; nothing typed is lost.
- **States:** `loading.js` skeletons for the list and the order; `error.js` with Try again; an unknown id is the order's own not-found page with Back to orders.

### Offers and bundles

Line 4. `/admin/offers`, `/admin/offers/[id]` (`new` is the create form), `/admin/bundles` and `/admin/bundles/[id]`, on the same APIs as before; Bundles is a Growth nav item after Offers. Parts: `components/admin/offers/` and `components/admin/bundles/`.

Tabs by state with counts and a search by name or code (both reads). Writers get a Switch per row; turning off a live offer asks first. A bundle's own offer says "Part of bundle X" (a link to it) and has no switch for anyone.

"Check before you start" holds the live sentence (old and new side by side when editing), the details, "Try it" example carts, the warnings and "Still to do". Save sits under all of it and stays disabled until the rules are complete. An edit adds On/Off and Delete in the header and "Before your last change" with "Go back to previous settings". Every refusal is plain words; nothing typed is lost; leaving with unsaved changes asks first.
- **The picker (`RefCombobox`):** a Popover with a search box and a listbox on `GET /api/admin/refs` (Command and `cmdk` stay deferred). Enter or Space on the trigger opens it; typing searches; ArrowDown/ArrowUp/Home/End move the active option (`aria-activedescendant`); Enter picks; Esc closes with focus back on the trigger; a product with sizes opens its sizes (Backspace in the empty box goes back), one with a single size picks it at once. The live check (debounced) puts each reason on its product row or under the price and says the saving to the cent. "Turn on after saving" (off by default); a taken link and a refusal are said in words.
- **States:** a `loading.js` skeleton shaped like each list; empty states with "New offer" / "New bundle"; a failed reload says so with Try again; an unknown id is the not-found page.
- **Support:** the same lists and pages; no switches, Save, Delete or "Go back"; every field disabled; "New offer"/"New bundle" RoleGate-disabled with the reason; "Try it" works (it is a read: `POST /api/admin/offers/simulate`, listed in `READ_POSTS` in `scripts/support/read-controls.js`).

### Team

`/admin/settings/team` (Phase 2 line 8), gated `team.manage`. `components/admin/team/`: `TeamPage` (the screen, with `TeamNoAccess` and `TeamSkeleton`), `MembersTable` (with its Change role dialog), `InvitesTable`, `InviteDialog` (with `InviteLink`), `RoleSelect`, `RemoveDialog`, `TransferDialog`; words and rules in `team-words.js`. Data: the server renders `teamView()` (`lib/admin/team.js`); every write to `POST /api/admin/team` answers with the fresh view.

- **Layout:** `PageHeader` (breadcrumb Settings / Team, one sentence; "Transfer ownership" for an owner and "Invite someone"); a Members card (the kit's `DataTable`: name with a "You" badge, email, role in words, joined date; owners first; per row "Change role" and "Remove") and a Pending invites card (email, role, sent, expires; "Send a new link" and "Revoke"; an `EmptyState` when none).
- **Who sees what:** every write control goes through `RoleGate` in hide mode. An owner's row and an owner invite need `team.owner`, any other `team.manage`; so an admin sees no controls on owner rows or owner invites and no Transfer. No Remove on your own row. The role select is native (the phone's own picker) and offers Owner only to an owner, each role with one line of what it can do.

- **States:** `loading.js` (title row and skeleton cards); "Team accounts need the platform control plane" when the store has none; a failed read in words with Try again (`data-read-control`); staff and support get the no-access card and no member data at all.
