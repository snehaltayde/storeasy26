# Phase 5 plan: uploadable themes (roadmap Phase 2B)

Architect plan, 2026-11-25 21:15 IST. Owner target: Phase 5 closed by midnight.

## Findings that shape the plan
1. A look is already a draft field that only Publish makes live: `doc_design.body.settings.theme = {kit, version, applied_at}` (validated in `lib/registry/settings.js:385`). Publishing `doc_design` goes through releases + `publish_log`, then `afterCommit` writes `config.theme_pin` (`lib/documents/after-commit.js`). An uploaded theme is one more key there, `package: "thm_…"`, so publish, preview, rollback, `publish_log` and the operator pin reuse existing code.
2. Preview exists: `POST /api/admin/preview-session {create}` and `{showDesign:{sid,on}}` lay the design draft over the live release for signed-in preview browsers (`lib/content/resolve.js` contentSource → `preview: true`). No new preview mechanism.
3. Package templates map onto `SURFACE_TEMPLATE_CHOICES` (`lib/cms/defaults.js`: pdp classic|editorial, collection standard|sidebar, header standard|centered, footer columns|minimal) and registry home sections (`lib/registry/sections.js`, `product_main` excluded).
4. No zip dependency; the zip + `.stml` + raw CSS design in `lib/types/ecosystem.ts` §B conflicts with "data only" and is rewritten in step 0.
5. `storefront.publish` (admin, owner) is the founder's Publish; `storefront.write` (staff and up) drafts. The `theme` cache namespace is reserved in `lib/cache.js`.

## Package format `storeasy-theme/1` (fixed now so lines 1 and 2 run in parallel)
One JSON file, ≤ 256 KB, UTF-8. Unknown keys anywhere are refused.
```json
{ "format": "storeasy-theme/1", "id": "aurora", "name": "Aurora", "version": "1.2.0",
  "author": { "name": "…" }, "description": "≤ 300 chars", "base": "pulse | glow",
  "tokens":   { /* exactly the keys validateBrand() accepts */ },
  "surfaces": { "header": { "bg": "#hex", "fg": "#hex", "muted": "#hex" }, "hero": { "bg": "", "fg": "", "muted": "" } },
  "templates": { "pdp": "classic|editorial", "collection": "standard|sidebar", "header": "standard|centered",
                 "footer": "columns|minimal", "home": { "sections": [ { "kind": "hero", "settings": { } } ] } },
  "styles": [ { "part": "hero-title", "set": { "letter-spacing": "-0.02em", "color": "role:accent" } } ] }
```
- `styles` is the constrained CSS: ≤ 60 rules; selector and every value generated by Storeasy.
  - Parts allowlist: `header`, `header-link`, `announcement`, `footer`, `footer-link`, `hero`, `hero-title`, `hero-subtitle`, `section`, `section-heading`, `product-card`, `product-card-title`, `product-card-price`, `collection-card`, `badge`. None is inside buy box, cart or checkout.
  - Properties allowlist with value rules: `color`/`background-color`/`border-color` = `#rgb`|`#rrggbb`|`role:<ROLE_IDS>`; `border-width` 0–4px; `border-radius` 0–48px; `font-weight` 300–900 step 100; `font-style`; `letter-spacing` -0.05em..0.3em; `text-transform`; `text-align`; `padding-block`/`padding-inline` 0–8rem; `gap` 0–4rem; `box-shadow` none|sm|md|lg presets.
  - Output: `:where([data-theme="<id>"]) [data-part="<part>"]{…}`. Never `display`, `position`, `visibility`, `opacity`, `z-index`, `content`, `pointer-events`.
- No assets in Phase 5: image fields in home sections must be empty; a `med_` reference or any URL is refused. No media keys written.

**Refusals** (run first, deep walk over every key and string; strings normalised first: entities decoded, whitespace and control/zero-width chars stripped, case folded). Each names its place: `"<plain words> (at templates.home.sections[2].settings.body)"`, up to 20 issues.
- `<script` → "Themes can't contain scripts."
- `on…=` in markup, or a key matching `/^on[a-z]/i` → "Themes can't contain event handlers like onclick."
- `javascript:`, `vbscript:`, `data:text/html` → "Themes can't contain javascript: links."
- `@import` → "Themes can't import other files."
- `url(` → "Themes can't load files with url(…)."
- `expression(`, `-moz-binding`, `behavior:` → refused.
- `<style`, `<iframe`, `<object`, `<embed`, `<link`, `<meta`, `<base`, `<svg` → "Themes can't contain HTML tags like <iframe>."
- `http(s)://` or `//host` outside a registry `link` field → "Themes can't load anything from other websites."
- keys `script(s)`, `js`, `css`, `html`, `head`, `import(s)`, `__proto__`, `constructor`, `prototype` → `Themes are data only: remove "scripts".`
- > 12 levels of nesting or > 5,000 nodes → refused.
- not JSON → "This file isn't a theme package: it isn't valid JSON."
- over the cap → 413 "Theme packages can be up to 256 KB."

Further checks: `tokens` → `validateBrand`; `home.sections` → registry validator; `surfaces` and any style rule setting both `color` and `background-color` need 4.5:1 contrast (`contrastRatio`).

```sql
-- migrations/tenant/0034_theme_packages.sql (additive)
CREATE TABLE IF NOT EXISTS theme_packages (
  id TEXT PRIMARY KEY,             -- "thm_" + 16 hex; immutable once written
  slug TEXT NOT NULL, version TEXT NOT NULL, name TEXT NOT NULL,
  author TEXT, description TEXT, base_kit TEXT NOT NULL,
  package TEXT NOT NULL,           -- normalised, validated JSON
  sha256 TEXT NOT NULL, size_bytes INTEGER NOT NULL,
  status TEXT NOT NULL DEFAULT 'installed',  -- installed | archived (never deleted)
  uploaded_by TEXT NOT NULL, uploaded_at TEXT NOT NULL, archived_by TEXT, archived_at TEXT);
CREATE UNIQUE INDEX IF NOT EXISTS idx_theme_packages_slug_ver ON theme_packages(slug, version);
CREATE INDEX IF NOT EXISTS idx_theme_packages_status ON theme_packages(status, uploaded_at);
```

## Line 1: an admin uploads a theme package; unsafe ones are refused in plain words
**Features (floor)**
1. `/admin/themes` (nav "Themes", Store group, `storefront.read`): built-in looks (Pulse, Glow) + uploaded packages (name, version, author, token swatch, uploaded by/when); plain empty state; "Archived" filter.
2. "Upload theme" (`themes.manage`): pick a file, read as text in the browser, POST it; button disabled with progress while uploading. Success summary: base, templates, section count, style-rule count. Refusal lists every issue with its location. Size checked on `Content-Length` and again while streaming (no header or a lying header still stops at 256 KB + 1).
3. Same slug+version → 409 "Aurora 1.2.0 is already installed. Raise the version to upload a change." New version → new row.
4. At most 30 installed packages per store.
5. `/admin/themes/[id]`: tokens, surfaces, templates, section list and style rules in words; "Download package" returns the stored normalised JSON (`storefront.read`).
6. Archive (`themes.manage`, AlertDialog): 409 if the package is live or in the current `doc_design` draft; an archived package still renders if an old release is rolled back.
7. Audit `themes.upload` `{slug, version, sha256}`, `themes.archive`. Refusals → slog `theme_upload_refused` `{codes, size}`, no content.
8. Staff, support, op-support see list and detail with no upload/archive controls.

**Files:** `lib/themes/package-guard.js` (pure scanner); `lib/themes/package-validate.js` (`parseThemePackage(text)` → `{pkg}`|`{issues}`); `lib/themes/packages.js` (list, get, upload, archive, `bodyTextCapped`); `lib/platform/authz.js`; `app/api/admin/themes/route.js` (GET list, POST upload); `app/api/admin/themes/[id]/route.js` (GET; POST `{archive}`); `lib/admin/nav.js`; `app/(console)/admin/(authed)/themes/page.js`, `.../themes/[id]/page.js`; `components/admin/themes/{ThemeLibrary,UploadThemeDialog,UploadIssues,ThemeDetail,ArchiveThemeDialog}.js`; `scripts/test-theme-packages.js` + `test:theme-packages`; support rows; `scripts/drills/themes/stage-upload.mjs`; `docs/UI.md` ("Themes").

**Tests (`test-theme-packages`):** every refusal plus obfuscations (`<ScRiPt`, `java\tscript:`, `&#106;avascript:`, `onClick` key, `__proto__`, depth, size); 413 with a lying `Content-Length`; every role-matrix row; support reads with canaries (another store's package; no upload/archive in the action list); archive of live/draft refused; audit rows.

**Drill stage:** owner uploads `aurora`, then an evil package and sees the issues; staff sees no Upload.

## Line 2: a shopper sees the uploaded theme; cart, buy box and checkout stay Storeasy's own
**Features (floor)**
1. `lib/themes/live-package.js` (Edge-safe, no `node:*`): `packageFor(theme)` reads by id via `cachedTenantRead("theme", ["pkg", id])` + React `cache()`; rows are immutable so the cache stays valid; no table / missing / corrupt row → base kit + slog `theme_package_missing`.
2. `app/(storefront)/layout.js`: `data-theme="<slug>"` beside `data-kit`; `brandCssVars(brand, {kit, surfaces: pkg.surfaces})` (so `lib/brand.js` `kitSurfaces`, `brandRoles`, `checkBrand` gain optional `surfaces`); a `<style>` with `compileStyles(pkg.styles)` in the same element as brandCss.
3. `resolvedSurfaceTemplates()` / `effectiveSurfaceTemplate` take the theme's templates as defaults. Precedence: entity → founder family → theme → platform.
4. `data-part="…"` hooks for the 15 parts in Header, Footer, AnnouncementBar, hero, section headings, product and collection cards.
5. `data-protected="buy-box|cart|checkout"` on the PdpLayouts buy box, cart drawer and page, and `CheckoutFlow`; no `data-part` inside them.
6. Operator kill switch `ff_theme-packages` (Phase 4 `isKilled` pattern): off → every store renders its base kit and uploads are refused with "Uploaded themes are turned off by Storeasy right now."

**Files:** `lib/themes/live-package.js`; `lib/brand.js`; `lib/cms/defaults.js`; `lib/content/resolve.js`; `app/(storefront)/layout.js`; the part-tagged components (builder greps real names: Header, Footer, AnnouncementBar, hero, cards, `components/pdp/PdpLayouts.js`, cart components, `components/checkout/CheckoutFlow.js`); `scripts/test-theme-render.js` + `test:theme-render`; `scripts/drills/themes/stage-render.mjs`.

**Tests (`test-theme-render`, anonymous shopper):** store A's live package shows `data-theme` and its CSS, store B none; a draft-only package is absent from anonymous HTML; buy box/cart/checkout markup byte-identical with and without the theme apart from token variables; static scan: no `data-part` under `data-protected`; compiled CSS has no `url(`, `@`, `<` or `}` injection even from a hand-tampered row; kill flag → base kit; missing package → base kit; transitive import scan from `layout.js` finds no `node:*`; measure added latency.

**Drill stage:** seeded live aurora visible on home and a PDP; add to cart and checkout still work.

## Line 3: an admin switches between installed themes, with a preview before publishing
**Features (floor)**
1. "Use this theme" (`storefront.write`) on library cards and detail: writes a draft of `doc_design` `settings.theme = {kit: base, version: 1, package: id, applied_at}` with `revision` concurrency (409 "Someone else changed your design just now"). "Also use its colours" (default on) writes `settings.brand` from tokens. "Also use its home layout" (default off) writes a `doc_home` draft, replacing the current draft only after a confirm. Choosing a built-in look clears `package`.
2. Badges "Live" and "In your draft". "Preview" creates/reuses a preview session with `showDesign:on` and opens the store in a new tab; the preview bar says the theme isn't live.
3. "Publish" (`storefront.publish`) calls the existing `doc_design` publish (release, `publish_log`, audit). `publishBlockers` (`kits.js`) refuses an archived/missing package ("This theme was archived. Choose another before publishing.") and runs `checkBrand` with package surfaces. Staff see "Ask an admin to publish".
4. `themePinOf`/`writeThemePin` carry `package`, `slug`, `version`; operator `GET /api/platform/themes` and `components/platform/operations/Themes.js` show the uploaded theme per store; Releases rollback restores the previous theme.
5. `DesignForm` ThemeControl shows "Theme: Aurora 1.2.0 (uploaded). Change it on Themes", read-only for packages.
6. Audit `themes.apply` `{package, withBrand, withHome}`.

**Files:** `lib/themes/packages.js` (`applyPackage`); `lib/themes/kits.js`; `lib/documents/after-commit.js`; `lib/types/tenant.ts` (`ThemePin.package`); `app/api/admin/themes/[id]/route.js` (`{apply}`); `app/api/platform/themes/route.js`; `components/platform/operations/Themes.js`; `components/admin/themes/{ApplyThemeDialog,ThemeDraftBar}.js`; `components/admin/editor/fields/DesignForm.js`; `scripts/test-theme-switch.js` + `test:theme-switch`; `scripts/drills/themes/stage-switch.mjs`.

**Tests (`test-theme-switch`):** apply leaves anonymous live HTML unchanged, preview session shows it; publish switches theme, writes `publish_log` + audit in one batch and `theme_pin.package`; staff apply ok, publish 403; support apply 403; archived package blocks publish; rollback renders the older package.

**Drill stage:** owner applies Aurora → previews (new tab shows it, anonymous tab doesn't) → publishes → anonymous sees it → switches back to Pulse and publishes.

## Risks
1. Style containment: tokens pass `checkBrand` at publish; parts/properties allowlists keep layout out. Reviewer tries to break the compiler with a hand-edited DB row.
2. Refusal-scanner obfuscation coverage (entities, zero-width, case) is the security core: dedicated security review.
3. Layout latency: one cached read per page; measured in `test-theme-render`.
4. Time: step 0 within ~20 minutes or line 2 runs second (not cut).
5. `data-part` edits in shared storefront components can ripple into the `sf-styles` drill: run once in the phase suite.
